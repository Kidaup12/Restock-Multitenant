# Moving the system to another Supabase project and Railway workspace

Everything except the database is redeployed from a commit in minutes. The database is not,
and neither are the four Shopify connections that depend on secrets travelling intact. This is
the order to do it in, and the checks that decide whether it worked.

The mechanics of dump-and-restore are in `docs/RESTORE-DRILL.md` and were rehearsed on
2026-08-26. Read that first; this document is the cutover around it.

## Decide these before touching anything

**Does the public domain change?** This is the biggest fork in the road.

The web app's origin is `SHOPIFY_APP_URL`, and it builds two things: the OAuth `redirect_uri`
and the webhook callback Shopify calls back on. Three of the live workspaces connected using an
app **the merchant created in their own Shopify admin**, with a redirect URI pointing at the
current origin.

- **Domain stays the same** — nothing merchant-facing changes. Straightforward.
- **Domain changes** — every one of those merchants must edit the redirect URI on their own
  Shopify app before their next reconnect, and webhooks re-register against the new origin.
  That is a coordinated change with other people's businesses, not a config edit. Plan it as
  its own piece of work with notice, not as part of a hosting move.

**Which plan is the destination on?** A free-tier project has no point-in-time recovery and
pauses after inactivity. This system syncs four shops every fifteen minutes and forecasts twice
an hour; a paused project is an outage. Confirm the tier deliberately — `docs/RESTORE-DRILL.md`
makes the same point about backups, and it is the layer that fails quietly.

**Does the region change?** The region is part of every pooled connection string
(`aws-0-<region>.pooler.supabase.com`). Moving between regions rewrites all of them, not just
the project reference.

**Is the compute big enough?** Check the destination's instance size against the current one.
Connection headroom is the thing to look at rather than CPU: the nightly forecast has already
died twice on a one-connection pool, and the app and worker use different `connection_limit`
values for exactly that reason (see `deploy/ENVIRONMENT.md`).

## Two secrets must travel unchanged

Both of these are in `deploy/ENVIRONMENT.md`; the point here is that a migration is when they
get regenerated by accident.

- **`TOKEN_ENCRYPTION_KEY`** — every Shopify access token in the database is AES-256-GCM
  ciphertext under this key, and the same value has to be on both the web and worker hosts.
  Restore the data with a *new* key and every connection becomes undecryptable: the app reports
  them broken and each merchant has to reconnect. Nothing about the data is recoverable without
  the original key.
- **`BETTER_AUTH_SECRET`** — signs sessions and the admin workspace cookie. A new one is not
  destructive, but it signs everyone out at once. Fine on a quiet evening; not what you want
  mid-onboarding.

Everything else can be regenerated or re-pointed.

## The cutover

Run it between cron ticks. The forecast fires at :07 and :37, the Shopify sync every fifteen
minutes; starting at, say, :15 gives the widest gap.

### 1. Stop the writers

Turn the worker's schedules off on the CURRENT Railway (`FORECAST_CRON`, `SHOPIFY_SYNC_CRON`,
`SNAPSHOT_CRON`, `EMAIL_CRONS`, `OPS_CRONS`, `POS_CRONS`, `COST_CRONS`) and redeploy, or stop
the service. A dump taken while a sync is writing is a dump of a half-finished sync.

Leave the web app up and read-only-in-practice — nobody is mid-purchase-order at 21:00, but
check the orders screen for a draft PO before you start, because a PO created during the window
is the one thing that would be lost on rollback.

### 2. Take the dump

Per `docs/RESTORE-DRILL.md`. The client must match the server's major version; you do not need
to install anything:

```bash
MSYS_NO_PATHCONV=1 docker run --rm -v "$PWD:/out" postgres:17-alpine \
  pg_dump "$PROD_DATABASE_URL" --format=custom --no-owner --no-privileges --file=/out/wezesha.dump
```

Use a **session-mode** connection, not the transaction pooler — pooling breaks `pg_dump` with an
error that looks like a permissions problem. Note the file size; a suspiciously small dump is
the failure this step exists to catch.

### 3. Prepare the destination

Create the two roles the application connects as, then restore:

```bash
psql "$NEW_DIRECT_URL" -c "CREATE ROLE wezesha_app LOGIN PASSWORD '<new>'; CREATE ROLE wezesha_service LOGIN PASSWORD '<new>' BYPASSRLS;"
pg_restore --dbname="$NEW_DIRECT_URL" --no-owner --no-privileges --clean --if-exists wezesha.dump
```

### 4. Put the grants back

`--no-privileges` is what stops the restore failing on every `ALTER … OWNER`, and it also drops
the grants. Without this step `wezesha_app` holds no table privileges at all and the app answers
`permission denied for table Product` — which reads like a broken restore rather than a missing
GRANT. Same statements the roles-and-grants migration issues:

```bash
psql "$NEW_DIRECT_URL" -c "
GRANT USAGE ON SCHEMA public TO wezesha_app, wezesha_service;
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA public TO wezesha_app, wezesha_service;
GRANT USAGE, SELECT ON ALL SEQUENCES IN SCHEMA public TO wezesha_app, wezesha_service;"
```

### 5. Prove the restore before pointing anything at it

All five, in this order. A restore that completes is not a restore that worked.

1. **Row counts match, table by table** — compare against the source, not against a feeling.
   `Product`, `SalesHistory`, `Order`, `PurchaseOrder`, `Supplier`, `Tenant` at minimum.
2. **RLS is enabled *and* forced** on every table carrying a `tenantId`. The auth-side tables
   (`Account`, `PlatformAdmin`, `Session`, `User`, `Verification`) and `WebhookEvent` carry no
   `tenantId` and are expected to differ.
3. **RLS actually bites.** Connect as `wezesha_app`, not as the owner — a superuser bypasses RLS
   and reads every row either way, so running this as the owner tells you nothing:
   ```bash
   psql -U wezesha_app -c 'select count(*) from "Product";'                                   # must be 0
   psql -U wezesha_app -c "set app.tenant_id = '<a real tenant id>'; select count(*) from \"Product\";"   # must be > 0
   ```
   Read the tenant id as the owner first: asking for it through the restricted role with no
   context set returns nothing, so the second query silently checks an empty string.
4. **The migration ledger matches the repository** — `_prisma_migrations` comes across with the
   dump; confirm the newest rows are the ones in `packages/db/prisma/migrations`.
5. **The connection tokens still decrypt.** The check that catches a regenerated
   `TOKEN_ENCRYPTION_KEY`: point a local web app at the restored database with the key you
   intend to use, open Settings → Connections, and confirm a connected store still reads as
   connected rather than erroring.

### 6. Railway

Create the services in the destination workspace — worker, ws-gateway, and Redis — and copy the
environment across. Redis moves with it: in-flight queue jobs are lost, which is harmless
because every schedule re-fires. Point the deployment at the same branch the current one uses.

Bring the worker up with its schedules still OFF.

### 7. Switch the environment

New `DATABASE_URL`, `SERVICE_DATABASE_URL` and `DIRECT_URL` on both hosts, carrying the pooled
settings the current ones use (the app and worker differ deliberately). `TOKEN_ENCRYPTION_KEY`
and `BETTER_AUTH_SECRET` copied verbatim. Everything else per `deploy/ENVIRONMENT.md`.

### 8. Unfreeze, then prove it from the live app

Turn the schedules back on. Then confirm the system is actually working rather than merely up:

- Open the app, sign in, and load the Restock Planner for a real workspace — the buy list should
  render with its numbers, not an empty state.
- Wait for one sync tick and check a workspace's `IngestCursor.dataAt` moves.
- Wait for :07 or :37 and confirm a new forecast run wrote predictions.

A health endpoint answering 200 proves nothing here — it will answer happily against a database
with no grants and no rows.

## Rollback

Until step 7 the original is untouched and still authoritative: revert the environment variables
and turn the old schedules back on. After step 7, anything written on the new host has to be
carried back by hand — which is why the freeze window matters, and why a draft purchase order
created during it is the thing to check for.

## What breaks silently

- A regenerated `TOKEN_ENCRYPTION_KEY`. Nothing errors at restore time; it surfaces as four
  merchants apparently revoking us.
- Missing grants. Reads like a corrupt restore.
- RLS restored but never behaviour-tested. "Looks fine" and "leaking between workspaces" are
  indistinguishable without connecting as the restricted role.
- A free-tier project pausing on inactivity, so the buy list quietly goes stale.
- A changed public origin, which does not fail at cutover — it fails the next time a merchant
  reconnects or a webhook fires.
